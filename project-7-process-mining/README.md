# Кейс 7 (бонус). Process mining: восстановление процесса из логов

Домен: процессы на стыке с данными. Вместо того чтобы рисовать процесс по рассказам сотрудников, я поднимаю его из журнала событий системы и сверяю с регламентом.

---

## Зачем это

Нарисованная модель процесса показывает, как он *должен* идти. Логи системы показывают, как он идёт *на самом деле*. Process mining сводит их вместе и находит, где реальность расходится с регламентом — например, где пропускают обязательные шаги.

Беру процесс возврата товара из [кейса 1](../project-1-process-optimization/) и смотрю на него уже со стороны данных.

---

## Что в ноутбуке

[`notebooks/process_mining.ipynb`](notebooks/process_mining.ipynb):

1. **Журнал событий.** Генерирую синтетический лог на ~800 заявок. В него заложены основной путь, отказы, повторная проверка товара и случаи с пропущенной проверкой права.
2. **Варианты.** Смотрю, сколько реальных вариантов процесса встречается и как часто.
3. **Восстановление модели.** Inductive miner (PM4Py) строит модель процесса по логу.
4. **Проверка соответствия.** Сравниваю лог с моделью, считаю fitness и выделяю заявки, где регламент нарушен.
5. **Выводы.** Какие отклонения нашлись и что с ними делать.

Эталон процесса: *Создана заявка → Проверка права → Накладная → Товар сдан → Товар проверен → Возврат денег*. Лог генерируется с фиксированным сидом, поэтому результат воспроизводим.

## К чему приходит анализ

- **Реальный процесс сложнее нарисованного:** кроме основного пути в логе есть отказы, повторные проверки и заявки без проверки права.
- **Контрольное нарушение:** примерно у каждой двенадцатой заявки пропущен шаг «Проверка права на возврат» — возвраты уходят без проверки.
- **Повторная проверка товара** — петля, которая удлиняет процесс; стоит понять, почему товар проверяют дважды.

По таким находкам ставят контроли в системе (дальше нельзя без проверки права) и считают потери на петлях. Process mining показывает процесс по фактам из логов, а не по тому, как его описывают на словах.
