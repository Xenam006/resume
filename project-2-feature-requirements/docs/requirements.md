# Требования: «Семейный аккаунт»

## Бизнес-требования (BRD)

| ID | Требование | Зачем |
|---|---|---|
| BR-1 | Семья может объединить до 6 человек в один аккаунт с общими адресами и оплатой | Семьи и так делят один аккаунт, легализуем этот сценарий |
| BR-2 | Владелец контролирует траты участников (лимиты, подтверждение) | Главная боль родителей — держать бюджет под контролем |
| BR-3 | Подросток может заказывать сам в заданных рамках | Больше активных заказчиков |
| BR-4 | Данные членов семьи обрабатываются по 152-ФЗ | Без этого фичу нельзя запускать, требование юристов |
| BR-5 | Фича растит частоту заказов и retention, не нагружая поддержку | Экономическое обоснование вложений |

Цель (SMART): за 3 месяца после запуска хотя бы 20% активных аккаунтов подключают участника, а частота заказов у семейных аккаунтов на 15% выше, чем в контрольной группе.

## Функциональные требования

| ID | Требование | Приоритет |
|---|---|---|
| FR-1 | Создать семейный аккаунт и стать его владельцем | Must |
| FR-2 | Пригласить участника по телефону/ссылке с указанием роли (взрослый/подросток) | Must |
| FR-3 | Удалить участника; удалённый теряет доступ к общим данным | Must |
| FR-4 | Участники пользуются общими сохранёнными адресами | Must |
| FR-5 | Участники оформляют заказ на общий способ оплаты / кошелёк | Must |
| FR-6 | Система хранит, кто из участников оформил заказ | Must |
| FR-7 | Владелец задаёт подростку лимит трат (в ₽ за период) | Should |
| FR-8 | При превышении лимита заказ уходит на подтверждение владельцу (push) | Should |
| FR-9 | Общий список покупок, видимый всем участникам | Could |
| FR-10 | Уведомление участникам «кто-то оформил общий заказ» | Could |

## Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| NFR-1 | Безопасность | Участник видит только разрешённые данные; платёжные реквизиты не показываются участникам (токенизация) |
| NFR-2 | Приватность / 152-ФЗ | При приглашении участник даёт согласие на обработку ПДн; за ребёнка до 14 лет действует законный представитель |
| NFR-3 | Производительность | Проверка лимита и оформление заказа укладываются в 1 с в 95% случаев |
| NFR-4 | Надёжность | Двойного списания с общего кошелька нет (идемпотентность оплаты) |
| NFR-5 | Доступность | Онбординг в семейный аккаунт — не больше 3 экранов |

## User stories с критериями приёмки

### US-1. Создание семейного аккаунта
> Как пользователь, я хочу создать семейный аккаунт, чтобы объединить заказы и оплату с близкими.

- **Given** у пользователя обычный аккаунт, **When** он нажимает «Создать семейный аккаунт», **Then** он становится владельцем нового аккаунта и видит экран управления участниками.
- **Given** пользователь уже владелец семейного аккаунта, **When** он открывает создание ещё одного, **Then** система говорит, что владельцем можно быть только у одного.

### US-2. Приглашение участника
> Как владелец, я хочу пригласить члена семьи и задать ему роль, чтобы он заказывал на общих условиях.

- **Given** владелец на экране управления, **When** он вводит телефон и выбирает роль «взрослый», **Then** приглашённому приходит приглашение, а после согласия он появляется в списке с ролью «взрослый».
- **Given** в аккаунте уже 6 участников, **When** владелец приглашает ещё одного, **Then** система блокирует приглашение и показывает лимит.
- **Given** приглашённый открывает приглашение, **When** он вступает, **Then** перед вступлением ему показывают согласие на обработку персональных данных (NFR-2).

### US-3. Заказ подростком в пределах лимита
> Как подросток-участник, я хочу оформить заказ сам, чтобы не ждать родителей, оставаясь в разрешённой сумме.

- **Given** подростку задан лимит 1500 ₽/неделя и потрачено 0 ₽, **When** он оформляет заказ на 900 ₽, **Then** заказ проходит сразу, остаток лимита становится 600 ₽.
- **Given** остаток лимита 600 ₽, **When** подросток оформляет заказ на 800 ₽, **Then** заказ уходит на подтверждение владельцу, а подросток видит статус «Ожидает подтверждения».
- **Given** заказ ждёт подтверждения, **When** владелец его отклоняет, **Then** заказ отменяется, деньги с кошелька не списываются, подросток получает уведомление.

### US-4. Контроль трат владельцем
> Как владелец, я хочу видеть, кто и на сколько заказал, чтобы держать бюджет под контролем.

- **Given** в аккаунте несколько участников, **When** владелец открывает историю заказов, **Then** по каждому заказу видно, кто его оформил и на какую сумму.

Все истории отвечают INVEST: независимы, обсуждаемы, ценны, оцениваемы, малы, тестируемы — критерии приёмки проверяемы.

## Приоритизация MoSCoW

| Фича | Приоритет | Почему |
|---|---|---|
| Создание аккаунта, приглашение/удаление участников (FR-1…FR-3) | **Must** | Без этого фичи нет |
| Общие адреса и оплата (FR-4, FR-5) | **Must** | Главная ценность — заказывать на общее |
| Хранение автора заказа (FR-6) | **Must** | Нужно для контроля и поддержки |
| Лимиты и подтверждение (FR-7, FR-8) | **Should** | Сильно усиливают ценность для родителей, но v1 может выйти и без них на взрослых ролях |
| Общий список покупок (FR-9) | **Could** | Приятно, но не критично |
| Уведомления о заказах (FR-10) | **Could** | Улучшает прозрачность, можно позже |
| Раздельные выписки, банковские семейные карты | **Won't (v1)** | Высокая сложность, отдельная история |

Решение по v1: все Must плюс лимиты для подростков из Should. Контроль трат — ключевой мотив родителей и прямой драйвер retention, поэтому его тащу в первую версию.

## Метрики успеха

| Метрика | Гипотеза | Как измерим | Срок |
|---|---|---|---|
| Подключение семьи | ≥ 20% активных аккаунтов добавят участника | % аккаунтов с ≥2 участниками | 3 мес |
| Частота заказов | +15% у семейных vs контроль | A/B или сравнение когорт | 3 мес |
| Retention | +10 п.п. у семейных аккаунтов | когортный анализ | 6 мес |
| Обращения «чужой заказ/оплата» | −30% | теги обращений поддержки | 3 мес |
| Доля заказов подростков с подтверждением | мониторинг | доля заказов, ушедших на подтверждение | текущая |
