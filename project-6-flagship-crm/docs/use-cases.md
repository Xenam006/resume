# Сценарии использования: CRM для сети фитнес-клубов

## UC-1. Онлайн-запись на групповое занятие

| Поле | Значение |
|---|---|
| **Актор** | Клиент (основной), Система абонементов (вторичный) |
| **Предусловие** | Клиент авторизован, есть активный абонемент |
| **Триггер** | Клиент выбирает занятие в расписании |
| **Результат** | Создана бронь и зарезервировано место, либо предложена альтернатива |

**Основной сценарий:**
1. Клиент открывает расписание и выбирает занятие.
2. Система проверяет активный абонемент и остаток посещений.
3. Система проверяет наличие свободного места.
4. Условия выполнены → система создаёт бронь, уменьшает число свободных мест, отправляет подтверждение.

**Альтернативные сценарии:**
- 2a. Нет активного абонемента → система предлагает купить/продлить, бронь не создаётся.
- 3a. Мест нет → система предлагает лист ожидания (если включён) или другое занятие.
- 4a. Клиент уже записан на это занятие → повторная бронь не создаётся.

## UC-2. Продажа и продление абонемента

| Поле | Значение |
|---|---|
| **Актор** | Администратор |
| **Предусловие** | Клиент найден в базе (или создаётся) |
| **Триггер** | Клиент хочет купить/продлить абонемент |
| **Результат** | Создан/продлён абонемент, зафиксирована оплата |

**Основной сценарий:**
1. Админ находит клиента по телефону.
2. Админ выбирает тариф (срок, лимит, цена).
3. Админ подтверждает оплату.
4. Система создаёт абонемент (статус «активен», даты, остаток посещений) и запись об оплате.

**Альтернативные сценарии:**
- 1a. Клиента нет в базе → админ создаёт карточку (FR-1).
- 2a. У клиента есть активный абонемент → система предлагает продление: дата окончания увеличивается на срок тарифа.

## UC-3. Check-in и списание посещения

| Поле | Значение |
|---|---|
| **Актор** | Администратор |
| **Предусловие** | У клиента есть бронь/активный абонемент на сегодня |
| **Триггер** | Клиент пришёл в клуб |
| **Результат** | Посещение зафиксировано, остаток абонемента уменьшен |

**Основной сценарий:**
1. Клиент предъявляет QR/называет телефон.
2. Админ выполняет check-in.
3. Система фиксирует посещение, уменьшает остаток посещений, помечает бронь «посещено».

**Альтернативные сценарии:**
- 3a. Клиент уже отмечен на это занятие → повторное списание не выполняется (NFR-6).
- 3b. Абонемент истёк/заморожен → система блокирует check-in и сообщает причину.

## UC-4. Заморозка абонемента

| Поле | Значение |
|---|---|
| **Актор** | Администратор / Клиент |
| **Предусловие** | Активный абонемент, допускающий заморозку |
| **Триггер** | Запрос на заморозку на период |
| **Результат** | Абонемент заморожен, срок окончания сдвинут |

**Основной сценарий:**
1. Указывается период заморозки.
2. Система меняет статус на «заморожен» и сдвигает дату окончания на длину периода.
3. В период заморозки запись и check-in недоступны.
4. По окончании периода статус возвращается в «активен».
