# Требования: CRM для сети фитнес-клубов

## 1. Бизнес-требования (BRD)

| ID | Бизнес-требование | Обоснование |
|---|---|---|
| BR-1 | Единая база клиентов и абонементов по всей сети | Сейчас данные разрознены по клубам → теряются продления |
| BR-2 | Онлайн-запись на групповые занятия с контролем мест | Телефон + тетрадь дают двойные записи и неявки |
| BR-3 | Автоматический учёт посещений (check-in) | Ручная отметка ненадёжна, нет данных о загрузке |
| BR-4 | Напоминания о неявке и окончании абонемента | Прямой рычаг роста продлений и снижения неявок |
| BR-5 | Аналитика посещаемости, загрузки и продлений | Руководство управляет «на глаз» |
| BR-6 | Прозрачный учёт заморозок и оплат | Споры с клиентами, риск злоупотреблений |

**Цель (SMART):** за 6 месяцев после внедрения поднять долю продлений абонементов на ≥ 8 п.п. и снизить неявки на групповые занятия на ≥ 30% при сохранении времени обслуживания на ресепшене.

## 3. Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| NFR-1 | Производительность | Поиск клиента и проверка абонемента — ≤ 2 сек в 95% случаев |
| NFR-2 | Надёжность | Нельзя записать сверх вместимости (контроль на уровне БД/транзакции) |
| NFR-3 | Безопасность / 152-ФЗ | Разграничение прав (админ/управляющий/тренер); ПДн клиентов защищены, согласие на обработку |
| NFR-4 | Доступность | Онлайн-запись доступна клиенту 24/7 |
| NFR-5 | Масштабируемость | Единая система на 5 клубов с возможностью добавления новых |
| NFR-6 | Целостность | Одно активное посещение на клиента за занятие (нет двойного списания) |

## 4. User stories с критериями приёмки

### US-1. Продажа абонемента
> Как администратор, я хочу продать клиенту абонемент по тарифу, чтобы он мог посещать клуб.

- **Given** найден клиент, **When** админ выбирает тариф и подтверждает оплату, **Then** создаётся абонемент со статусом «активен», датами начала/окончания и записью об оплате.
- **Given** у клиента уже есть активный абонемент, **When** админ оформляет новый, **Then** система предлагает продление вместо дубля.

### US-2. Онлайн-запись на занятие
> Как клиент, я хочу записаться на групповое занятие сам, чтобы не звонить на ресепшен.

- **Given** у клиента активный абонемент с остатком посещений и на занятии есть места, **When** он записывается, **Then** бронь создаётся, место резервируется, приходит подтверждение.
- **Given** на занятии нет мест, **When** клиент записывается, **Then** система предлагает лист ожидания (если включён) или другое время.
- **Given** у клиента нет активного абонемента, **When** он записывается, **Then** система предлагает купить/продлить абонемент и бронь не создаётся.

### US-3. Check-in и учёт посещения
> Как администратор, я хочу отметить приход клиента, чтобы посещение списалось автоматически.

- **Given** у клиента есть бронь на сегодня, **When** админ делает check-in, **Then** посещение фиксируется, остаток по абонементу уменьшается, статус брони → «посещено».
- **Given** клиент уже отмечен на это занятие, **When** админ повторяет check-in, **Then** повторное списание не происходит (NFR-6).

### US-4. Заморозка абонемента
> Как клиент, я хочу заморозить абонемент на время отпуска, чтобы не терять оплаченные дни.

- **Given** активный абонемент, **When** оформляется заморозка на 10 дней, **Then** статус → «заморожен», дата окончания сдвигается на 10 дней, в этот период запись недоступна.

### US-5. Контроль истекающих абонементов
> Как управляющий, я хочу видеть клиентов с истекающим абонементом, чтобы вовремя их продлить.

- **Given** есть абонементы с окончанием в ближайшие 7 дней, **When** управляющий открывает отчёт, **Then** он видит список таких клиентов с контактами.

> Истории соответствуют INVEST; критерии приёмки сформулированы проверяемо (Given/When/Then).

## 5. Приоритизация MoSCoW

| Блок | Приоритет | Обоснование |
|---|---|---|
| База клиентов, абонементы, продажа/продление (FR-1…FR-5, FR-7) | **Must** | Ядро системы, без него нет CRM |
| Расписание и онлайн-запись, учёт посещений (FR-8, FR-9, FR-12) | **Must** | Главная операционная ценность |
| Заморозка, отмена, список для тренера, дашборды, сегменты (FR-6, FR-10, FR-13, FR-14, FR-15) | **Should** | Сильно повышают ценность, но v1 поедет и без них |
| Лист ожидания (FR-11) | **Could** | Приятно, не критично |
| Программа лояльности, мобильное приложение, турникеты, биометрия | **Won't (v1)** | Отдельные крупные инициативы |

**Решение по v1:** все Must + выбранные Should (напоминания об окончании абонемента и дашборд истекающих), так как именно они напрямую бьют в цель по продлениям (BR-4, BR-5).
